# ТЗ: MVP браузерного ASCII-рогалика

## 0. Как работать с этим ТЗ

Ты пишешь MVP пошаговой браузерной игры-рогалика с ASCII-графикой, вдохновлённой Dungeon Crawl Stone Soup (DCSS). Игровое состояние хранится на сервере, клиент только отображает его и отправляет команды.

Правила работы:
- Следуй архитектуре и структуре из разделов 2–3. Если что-то в ТЗ противоречиво или неясно — выбери самый простой вариант, запиши решение в `DECISIONS.md` и продолжай.
- Формулы боя, модель времени и шаблоны сообщений — **временные заглушки**. Они должны быть изолированы в отдельных модулях (раздел 6) так, чтобы их можно было полностью заменить, не трогая остальной код.
- Работай по этапам из раздела 12. После каждого этапа проект должен собираться, тесты проходить, а игра запускаться.
- Не добавляй ничего из раздела 11 («Вне рамок MVP»).

## 1. Цель MVP

Игрок открывает игру в браузере, создаёт персонажа, исследует подземелье из 3 уровней, сражается с монстрами в системе боя по частям тела, находит и надевает снаряжение с прочностью, получает и лечит раны, изучает найденное снаряжение бортовым компьютером и доходит до портала. Можно закрыть вкладку и, открыв её снова, продолжить ту же партию с того же места. Смерть окончательна.

Ключевые отличия от DCSS, которые MVP должен продемонстрировать:
1. **Нет богов.** Развитие персонажа — через изучение снаряжения (навыки) и само снаряжение.
2. **Бой по частям тела.** Удар случайно (по весам) приходится в конкретную часть тела. Ранения частей тела влияют на боевые возможности как у игрока, так и у монстров.
3. **Тело киборга.** Части тела игрока бывают органическими и бионическими; они по-разному повреждаются, лечатся и ремонтируются.
4. **Прочность предметов.** Снаряжение изнашивается и постепенно теряет эффективность.
5. **Изучение снаряжения.** Характеристики найденных предметов неизвестны, пока бортовой компьютер их не изучит.
6. **Подробные сообщения боя** на русском языке с корректными падежами и родом.

## 1.1. Сеттинг

Игрок — киборг из будущего, который в результате сбоя оказался в средневековом подземелье. В глубине подземелья находится портал, через который можно вернуться в своё время; дойти до него — цель игры.

Оружие из будущего при переносе вышло из строя, поэтому киборг вынужден пользоваться местным оружием и бронёй. Его бортовой компьютер (далее — «ядро») изучает найденное и снятое с врагов снаряжение по мере использования: чем дольше киборг сражается определённым типом оружия или носит определённый тип брони, тем лучше ядро его понимает и тем эффективнее киборг им пользуется. Это и есть прокачка навыков.

Монстры, предметы и подземелье — средневековые (крысы, волки, гоблины, орки, мечи, кольчуги). Элементы будущего есть только у самого игрока: его тело, ядро, интерфейс, ремонтные системы и портал.

Стилистика интерфейса и части сообщений: системные сообщения ядра выводятся в стиле HUD/терминала, например `[ЯДРО] Новый тип оружия: булава. Анализ начат.` или `[ДИАГНОСТИКА] Левая рука (бионика): повреждение 40%.` Сообщения о событиях в мире (бой, монстры) — обычным повествовательным текстом.

В будущих версиях (не в MVP, см. раздел 11) появится **виртуальный терминал**, через который киборг улучшает бионические части тела: силу рук, ног, зрение и т.д. В MVP нужно только заложить под это модель данных (раздел 5.4).

## 2. Стек

- Язык: **TypeScript** (strict) везде.
- Монорепо: **pnpm workspaces**.
- Сервер: **Node.js 20+**, WebSocket через библиотеку `ws`, HTTP — минимальный (можно `fastify` или встроенный `http`) только для раздачи клиента и health-check.
- Хранилище: **SQLite** через `better-sqlite3`.
- Клиент: **Vite + Vue 3** (Composition API) для интерфейса (меню, панели, инвентарь). Карта рисуется на **canvas** (не через DOM/Vue-компоненты на каждую клетку). Можно использовать `ROT.Display` из rot.js или свой простой рендерер символов на canvas.
- Генерация карт, FOV, поиск пути: **rot.js** (используется в `core`, работает и в Node).
- Тесты: **Vitest**.
- Линт/формат: ESLint + Prettier (базовые конфиги).

## 3. Структура репозитория

```
packages/
  core/      — вся игровая логика. Чистый TS, без сети, БД, DOM, таймеров, Math.random
  data/      — данные: планы тел, монстры, предметы, навыки, словоформы, шаблоны сообщений
  server/    — Node: WebSocket, сессии, загрузка/сохранение, запуск core
  client/    — Vite + Vue: рендер карты на canvas, панели, ввод
  shared/    — (опционально) типы протокола клиент↔сервер, если их неудобно держать в core
DECISIONS.md — журнал решений, принятых агентом
README.md    — как запустить (dev и prod), как запустить тесты
```

Корневые скрипты: `pnpm dev` (сервер и клиент одновременно), `pnpm build`, `pnpm test`, `pnpm start`.

## 4. Архитектурные принципы (обязательные)

1. **Сервер авторитетный.** Клиент не меняет состояние игры. Он отправляет команды и получает результат.
2. **Core — чистая функция.** Основной интерфейс:
   ```ts
   applyCommand(state: GameState, cmd: Command): { state: GameState; events: GameEvent[] }
   ```
   Допустима мутация копии внутри, но снаружи — детерминированный результат по входу.
3. **Детерминизм.** Весь рандом — только через сидированный ГПСЧ, состояние которого хранится в `GameState` (например, `ROT.RNG` с `getState/setState` или свой mulberry32/xoshiro). `Math.random` и `Date.now` в `core` запрещены. Одинаковые `state` + `cmd` → одинаковый результат.
4. **Состояние сериализуемо.** `GameState` — обычный JSON-совместимый объект (без классов с методами, без циклических ссылок, ссылки между сущностями — по id).
5. **Данные отдельно от кода.** Монстры, предметы, планы тел, шаблоны сообщений описываются данными в `packages/data`, а не отдельными классами на каждый вид.
6. **События, а не строки.** Core возвращает структурированные события (`attack`, `wound`, `itemDamaged`, `death`, ...). Превращение событий в русский текст — отдельный модуль (раздел 6.3), вызываемый на сервере перед отправкой клиенту.
7. **Изоляция заглушек.** Формулы боя, модель времени и генератор сообщений находятся каждый в своём модуле с узким интерфейсом (раздел 6).

## 5. Игровые системы

### 5.1. Карта и уровни

- Размер уровня: 80×40 клеток.
- Генерация: `ROT.Map.Digger` (комнаты и коридоры) для всех уровней; для одного из уровней можно `ROT.Map.Cellular` (пещеры) — на усмотрение.
- 3 уровня. На каждом есть лестница вверх `<` и вниз `>` (на 1-м нет вверх, на 3-м нет вниз). Уровни генерируются при первом посещении и сохраняются в состоянии.
- На 3-м уровне вместо лестницы вниз находится **портал** (символ `0` или `Ω`, ярко-голубой), охраняемый «финальным» монстром посильнее (раздел 5.6). Вход в портал (команда `>` на клетке портала) — **победа**: партия завершается со статусом `won` и показывается экран итогов.
- Типы клеток: пол `.`, стена `#`, дверь `+` (закрытая) / `'` (открытая), лестницы `<` `>`.
- Двери открываются движением в них.

### 5.2. Поле зрения и туман войны

- FOV: `ROT.FOV.PreciseShadowcasting`, радиус 8.
- Три состояния клетки для игрока: видима сейчас / видена раньше (запомнена, рисуется тусклым цветом, без монстров) / неизвестна.
- Клиент получает только то, что игрок видит или помнит. Полную карту и невидимых монстров сервер **не отправляет**.

### 5.3. Время (ЗАГЛУШКА, см. 6.2)

- Модель на основе энергии / стоимости действий в стиле DCSS: каждое действие стоит некоторое количество единиц времени (`aut`), у каждого существа есть скорость.
- Очередь ходов реализуется в модуле времени; `core` спрашивает у него, кто ходит следующим.
- Заглушка: все действия стоят 10 aut, скорость всех существ одинаковая, кроме одного быстрого монстра (раздел 5.6). Интерфейс модуля должен позволять в будущем разную стоимость действий и разную скорость.

### 5.4. План тела и ранения

Это центральная система MVP.

**План тела** — данные, описывающие набор частей тела существа:

```ts
type PartTag = 'grasp' | 'stance' | 'vision' | 'vital' | 'bite' | 'claw'

interface BodyPartDef {
  id: string              // 'left_arm'
  name: WordForms         // словоформы (раздел 5.8)
  tags: PartTag[]
  hitWeight: number       // относительная вероятность попадания
  maxHp: number           // в единицах «здоровья части», масштабируется от существа
  armorSlot?: SlotId      // какой слот брони защищает эту часть
  severable?: boolean     // можно ли отрубить (в MVP можно не реализовывать отрубание, но поле заложить)
}

interface BodyPlanDef {
  id: string              // 'humanoid', 'humanoid_fourarmed', 'quadruped'
  parts: BodyPartDef[]
}
```

**Обязательные планы тел в MVP:**
- `humanoid` — голова (`vision`, `vital`), торс (`vital`), левая рука (`grasp`), правая рука (`grasp`), левая нога (`stance`), правая нога (`stance`).
- `humanoid_fourarmed` — как гуманоид, но 4 руки (верхние/нижние). Нужен, чтобы проверить, что система работает не только для стандартного набора частей.
- `quadruped` — голова (`vision`, `vital`, `bite`), торс (`vital`), 4 лапы (`stance`; передние также `claw`). Для монстров-животных.

**Игрок** в MVP — всегда гуманоид-киборг. При создании персонажа выбирается «формация тела» (конфигурация киборга): `humanoid` или `humanoid_fourarmed`. Других различий (рас, статов) в MVP не нужно, кроме того, что следует из плана тела (например, у четырёхрукого больше слотов брони на руки).

**Материал части тела.** У каждой части тела существа есть материал: `organic` (органика) или `bionic` (бионика). У всех монстров MVP все части органические. У игрока — смесь, задаётся конфигурацией в данных. Предлагаемая стартовая конфигурация (числа и состав можно менять в данных):
- `humanoid`: голова и торс — органика; обе руки и обе ноги — бионика.
- `humanoid_fourarmed`: голова и торс — органика; верхние руки — бионика, нижние (дополнительные) — бионика; ноги — бионика.

Отличия материалов (конкретные числа — в модуле формул 6.1):
- **Органика:** естественно регенерирует; лечится бинтами и зельями; стадии ран называются как раны (`ушиб`, `рана`, `тяжёлая рана`).
- **Бионика:** **не регенерирует** и не лечится бинтами/зельями; ремонтируется **ремкомплектом** (тем же, что чинит снаряжение); стадии называются как повреждения (`царапины`, `повреждена`, `сильно повреждена`, `отказ`); может иметь более высокий базовый `maxHp` или встроенное поглощение урона.
- Сообщения боя и диагностики учитывают материал (по органике — «кровь», «рана», по бионике — «искры», «пробит корпус», «сервопривод заклинило» и т.п.).

**Заготовка под улучшения (для будущего терминала).** У бионической части тела в состоянии хранится уровень улучшения по осям (в MVP все нули, механики улучшения нет, но формулы уже должны читать эти поля через модуль 6.1):

```ts
interface BionicUpgrades {
  strength: number    // руки: урон; ноги: — (зарезервировано)
  precision: number   // руки: точность
  mobility: number    // ноги: уклонение / скорость
  sensors: number     // голова (если станет бионической): радиус обзора
  plating: number     // любая: поглощение урона
}
```

**Состояние части тела** у существа:

```ts
interface BodyPartState {
  defId: string
  material: 'organic' | 'bionic'
  hp: number
  wound: 'none' | 'bruised' | 'wounded' | 'crippled'  // 'severed' — заложить в тип, в MVP не обязательно
  upgrades?: BionicUpgrades                           // только для bionic
}
```

Стадия раны определяется порогами от `hp / maxHp` (пороги — в модуле формул, заглушка: >75% none, >50% bruised, >25% wounded, иначе crippled).

**Влияние ран** считается **по тегам**, а не по конкретным частям:
- `grasp`: ранения частей с этим тегом снижают точность и урон атак оружием. Если оружие держат несколько рук — учитывается худшая из держащих или среднее (на выбор, записать в DECISIONS.md). Для MVP оружие держит одна «основная» рука; при её `crippled` персонаж может атаковать другой рукой со штрафом либо автоматически перехватить оружие — выбрать простейший вариант.
- `stance`: снижают уклонение. (Влияние на скорость передвижения — заложить в интерфейс, в заглушке можно не применять.)
- `vision`: ранение головы уменьшает радиус FOV и точность.
- `bite` / `claw`: ранения снижают точность и урон соответствующих естественных атак монстра.
- `vital`: если `hp` любой `vital`-части падает до 0 — существо умирает.

**Общее здоровье:** помимо частей тела у существа есть общий пул HP. Существо умирает, если общий HP ≤ 0 **или** уничтожена `vital`-часть. Урон по части тела наносит урон и части, и общему пулу (точное соотношение — в формулах).

**Лечение и ремонт:**
- Естественная регенерация (только органика): раз в N ходов органическая часть тела восстанавливает немного hp; общий HP тоже регенерирует. Стадия `crippled` сама не лечится выше `wounded` без перевязки (это правило должно быть, конкретные числа — заглушка).
- Предмет «бинт» (только органика): применяется на выбранную органическую часть тела, снимает одну стадию раны и восстанавливает часть hp.
- Предмет «зелье лечения»: восстанавливает общий HP и понемногу все **органические** части.
- Предмет «ремкомплект»: применяется **либо** на предмет снаряжения (раздел 5.7), **либо** на бионическую часть тела — снимает одну стадию повреждения и восстанавливает часть hp. Выбор цели — в UI.
- При попытке применить бинт на бионику или ремкомплект на органику — сообщение об ошибке, ход не тратится.

### 5.5. Бой

Шаг атаки (порядок важен, реализация — в модуле формул 6.1):
1. **Выбор атаки атакующего:** оружие в руке (для игрока и вооружённых монстров) или естественная атака (укус, когти) для животных.
2. **Выбор части тела цели:** случайно, взвешенно по `hitWeight` частей цели. Навык атакующего в данном оружии **немного смещает** распределение в сторону `vital`-частей (заглушка: множитель к весу vital-частей).
3. **Проверка попадания:** точность атакующего (навык, модификаторы ран своих `grasp`/`claw`/`bite`/`vision` частей, прочность оружия) против уклонения цели (навык уклонения, модификаторы ран `stance`, штраф от тяжёлой брони — опционально).
4. **Броня:** если часть тела цели защищена броней в соответствующем слоте — броня поглощает часть урона (с учётом её прочности).
5. **Урон:** базовый урон оружия × модификаторы → наносится части тела и общему HP.
6. **Износ:** см. 5.7.
7. **Опыт навыков:** см. 5.9.
8. **События:** сформировать события `attackMissed` / `attackHit` / `woundChanged` / `itemDamaged` / `creatureDied` и т.д. со всеми данными, нужными для красивого сообщения (кто, кого, чем, в какую часть, тип урона, тяжесть результата, сколько поглотила броня).

У оружия есть **тип урона**: `slash` (рубящий), `pierce` (колющий), `blunt` (дробящий). Естественные атаки тоже имеют тип (укус — pierce, когти — slash). Тип урона пока влияет только на сообщения; в формулах заглушка может его игнорировать, но параметр должен передаваться.

Игрок атакует, двигаясь в клетку с монстром (как в DCSS).

### 5.6. Монстры

5 видов монстров (данные в `packages/data`):

| id | символ | план тела | атака | особенность |
|---|---|---|---|---|
| rat | `r` | quadruped | укус | слабый, частый на 1 уровне |
| jackal | `j` | quadruped | укус | ходит стаями по 2–3 |
| goblin | `g` | humanoid | оружие (кинжал), носит кожаную броню на торсе | может выпадать его снаряжение |
| wolf | `w` | quadruped | укус + когти | быстрый (скорость выше игрока — проверка модели времени) |
| orc_warrior | `O` | humanoid | оружие (топор), броня на торсе и голове | «финальный» монстр 3-го уровня |

Монстры с оружием и бронёй используют **тот же** механизм снаряжения и прочности, что и игрок. Их предметы выпадают при смерти (с текущей прочностью).

ИИ (простой):
- Если видит игрока — идёт к нему по пути (`ROT.Path.AStar`) и атакует при соседстве.
- Если не видит — бродит случайно или стоит.
- Если общий HP < 25% или `stance`-части в `crippled` — с некоторой вероятностью пытается отступить (это нужно, чтобы раны ощущались и у монстров). Можно упростить, но поведение должно присутствовать.
- Раненый монстр с `crippled` ногами двигается реже (через модуль времени или пропуск ходов — на выбор).

Расстановка: 6–12 монстров на уровень, состав зависит от глубины.

### 5.7. Предметы и прочность

Типы предметов:
- **Оружие** (слот: рука): кинжал (pierce), короткий меч (slash), булава (blunt), топор (slash). У каждого: базовый урон, точность, тип урона, навык (`short_blades`, `long_blades`, `maces`, `axes`), max прочность.
- **Броня** (слоты): шлем (голова), кожаная куртка / кольчуга (торс), перчатки/наручи (руки — на каждую руку отдельно или парой; для четырёхрукого — 2 пары), поножи / сапоги (ноги). У каждой: поглощение урона, max прочность.
- **Расходники:** бинт, зелье лечения, ремкомплект.

Прочность:
- У каждого экземпляра снаряжения `durability` и `maxDurability`.
- Износ оружия: при каждом попадании; сильнее при ударе по части, закрытой бронёй.
- Износ брони: при каждом попадании в часть тела, которую закрывает **именно этот** предмет.
- **Эффективность** — функция от доли прочности с порогами, а не линейная (заглушка, например: ≥75% → 100%, ≥50% → 85%, ≥25% → 65%, >0% → 40%, 0% → предмет сломан).
- Сломанный предмет (0) остаётся в инвентаре/надетым, но не даёт бонусов (оружие сломанное — бьёт как кулак со штрафом; это допустимо упростить).
- **Ремкомплект:** восстанавливает часть прочности выбранного предмета. Сломанный предмет чинится тоже. Тот же ремкомплект ремонтирует бионические части тела (раздел 5.4) — это намеренный ресурсный выбор для игрока.
- **Разборка** (команда `D` или пункт в инвентаре): предмет уничтожается, ядро получает данные об **этом типе** предмета (бонусный опыт соответствующего навыка, раздел 5.9). Сломанные предметы дают столько же данных, сколько целые (заглушка), — поломка не должна быть чистой потерей.
- Прочность и её состояние видно в UI (текстом и цветом).

**Изучение (опознание) предметов:**
- У каждого **типа** предмета (кинжал, булава, кольчуга, ...) есть статус изученности ядром: `unknown` → `partial` → `known`. Статус хранится у игрока, а не у экземпляра: изучив булаву, киборг знает все булавы.
- `unknown`: в UI видны только название и символ; урон/точность/поглощение/макс. прочность показаны как `??`. Текущая прочность видна в процентах приблизительно (`~70%`).
- `partial`: видны приблизительные значения (диапазоны или округление).
- `known`: видны точные значения.
- Переход между статусами — по накопленным данным об этом типе: использование в бою (атака оружием, получение ударов в броню), ношение, разборка. Пороги — заглушка в модуле формул.
- При смене статуса — системное сообщение ядра (`[ЯДРО] Анализ завершён: булава. Характеристики внесены в базу.`).
- Статус изученности влияет **только на отображение** в MVP; эффективность в бою определяется навыками (5.9).

Подбор (`g` или `,`), инвентарь (`i`), надеть/снять (`w`/`W` для оружия, `P`/`R` для брони — или единое окно экипировки), применить (`a` или `q`), выбросить (`d`). Размер инвентаря: 20 слотов (буквы a–t).

### 5.8. Сообщения боя (ЗАГЛУШКА с правильным каркасом, см. 6.3)

Тексты — временные, но **каркас обязателен**: словоформы, род, сборка из шаблонов.

Словоформы:

```ts
interface WordForms {
  nom: string; gen: string; dat: string; acc: string; ins: string; prep: string
  gender: 'm' | 'f' | 'n' | 'pl'
  animate?: boolean
}
```

Словоформы нужны для: названий монстров, игрока («ты»), частей тела, предметов.

Шаблоны выбираются по ключу из осей: тип события × тип урона × тяжесть результата (промах / слабый / средний / сильный / рана перешла в новую стадию / смерть). Для части тела — подставляются нужные падежи. Для глаголов — формы по роду и лицу (ты бьёшь / гоблин бьёт / гоблинша бьёт; ты промахиваешься / волк промахивается; …ся/…ась/…лось в прошедшем, если используется прошедшее время).

Пример формата (конкретный синтаксис шаблонов — на усмотрение, но описать его в README):

```
"{attacker.nom} {verb:бить} {target.acc} по {part.dat} {weapon.ins}"
→ «Гоблин бьёт тебя по левой руке кинжалом.»
```

Требования к заглушке:
- Минимум 2–3 варианта шаблона на каждую комбинацию «тип события × тип урона» (варианты выбираются случайно через ГПСЧ сообщений — он может быть отдельным, недетерминированность текста допустима, но лучше детерминированно).
- Отдельные шаблоны для: перехода раны в новую стадию («левая рука гоблина повреждена/искалечена»), поглощения броней, износа и поломки предмета, смерти.
- Проверка тестами, что для каждого монстра и части тела сообщения собираются без незаполненных плейсхолдеров.

Лог сообщений на клиенте: последние ~100 сообщений, новые выделены цветом.

### 5.9. Навыки (база знаний ядра)

В сеттинге навыки — это степень освоения ядром определённых классов оружия и брони и боевых алгоритмов. Без богов это основная прогрессия.

Навыки:
- Оружейные: `short_blades`, `long_blades`, `maces`, `axes`, `unarmed`.
- Броня: `light_armour`, `heavy_armour` (кожа — лёгкая, кольчуга — тяжёлая; шлемы/перчатки/поножи относятся к классу по данным предмета).
- Общие алгоритмы: `fighting` (общий боевой), `dodging`.

Модель (заглушка, позже будет переработана):
- Уровень навыка 0–27 (как в DCSS). На старте все оружейные и броневые навыки — 0, кроме небольшого стартового значения у выбранного стартового оружия (ядро успело изучить его до начала игры) и `fighting`/`dodging` (базовые алгоритмы).
- Данные (опыт) поступают в навыки **по факту использования**: атака оружием → навык класса этого оружия и `fighting`; уклонение от атак → `dodging`; удар в часть тела, закрытую броней → навык класса этой брони; разборка предмета → навык его класса. Плюс опыт за убийство монстров распределяется по навыкам, использованным в этом бою. Простейшая схема: копить счётчики использования и распределять их.
- Те же события использования продвигают изученность конкретного **типа** предмета (раздел 5.7) — это две связанные, но раздельные величины: навык класса (`long_blades`) и изученность типа (`короткий меч`).
- Навыки влияют на формулы через модуль 6.1.
- Экран навыков (`m`) оформлен как «База знаний ядра»: уровни и прогресс навыков, а также список встреченных типов предметов с их статусом изученности. Только просмотр.

### 5.10. Создание персонажа и смерть

- Создание: ввод обозначения киборга (имени), выбор конфигурации тела (`humanoid` / `humanoid_fourarmed`), выбор стартового оружия (кинжал / короткий меч / булава — «подобрано у входа, ядро успело его изучить»). Стартовое снаряжение: выбранное оружие (тип сразу `known`), кожаная куртка (тип `partial`), 2 бинта, 1 зелье лечения, 2 ремкомплекта.
- Вступительный экран: 2–3 строки о сбое переноса и цели (найти портал). Текст — заглушка.
- Смерть: партия помечается `dead`, дальнейшие команды не принимаются, клиент показывает экран итогов (имя, глубина, кем убит, количество ходов, последние ~10 сообщений лога). Кнопка «Новая игра».
- Победа (вход в портал): партия помечается `won`, экран итогов в той же форме с другим заголовком.

## 6. Изолированные модули-заглушки

Каждый модуль — отдельная папка в `packages/core/src/`, с файлом `index.ts`, экспортирующим только интерфейс, и `README.md` внутри с описанием, что это заглушка и какие функции ожидаются.

### 6.1. `combat/formulas`

Все числа и формулы боя: шанс попадания, выбор части тела, урон, поглощение броней, пороги стадий ран, модификаторы ран по тегам, кривая эффективности от прочности, износ, регенерация, распределение опыта. Остальной код вызывает только функции этого модуля и **не содержит** собственных боевых констант.

Примерный интерфейс:

```ts
chooseHitPart(rng, attacker, target, attack): BodyPartState
rollHit(rng, ctx: AttackContext): { hit: boolean; roll: number; chance: number }
rollDamage(rng, ctx: AttackContext): number
armourAbsorb(rng, ctx: AttackContext, armour?: ItemInstance): number
woundStageFor(part: BodyPartState, def: BodyPartDef): WoundStage
woundModifiers(creature): { accuracyMul: number; damageMul: number; evasionMul: number; fovDelta: number; ... }
durabilityEfficiency(item): number
durabilityWear(ctx, item, role: 'weapon' | 'armour'): number
regenTick(creature): RegenResult
```

### 6.2. `time`

Очередь ходов и стоимость действий. Интерфейс должен позволять: разную стоимость действий, разную скорость существ, модификаторы скорости от ран. Заглушка — описанная в 5.3.

### 6.3. `messages` (может жить в `server` или отдельном пакете `messages`, но не в логике `core`)

`renderEvents(events: GameEvent[], viewerId: string): LogMessage[]` — превращает события в русский текст. Шаблоны и словоформы — в `packages/data`. Код модуля отвечает только за выбор шаблона, склонение и подстановку.

## 7. Протокол клиент ↔ сервер

WebSocket, сообщения в JSON, типы — общие (`shared` или экспортируются из `core`).

Клиент → сервер:
```ts
type ClientMsg =
  | { type: 'hello'; token?: string }                // переподключение по токену
  | { type: 'newGame'; name: string; bodyPlan: string; startWeapon: string }
  | { type: 'command'; seq: number; cmd: Command }    // seq — порядковый номер от клиента
```

Сервер → клиент:
```ts
type ServerMsg =
  | { type: 'welcome'; token: string; hasActiveGame: boolean }
  | { type: 'view'; seq: number; view: PlayerView; messages: LogMessage[] }
  | { type: 'gameOver'; summary: GameSummary }
  | { type: 'error'; message: string }
```

`PlayerView` — **только то, что игрок должен видеть**: видимые и запомненные клетки, видимые монстры (с их видимым состоянием ран — например, «левая лапа: искалечена»), полное состояние игрока, инвентарь, навыки, глубина, номер хода. Для MVP допускается отправлять полный `PlayerView` после каждой команды (без дельт).

Команды (`Command`): `move {dir}`, `wait`, `pickup`, `drop {itemId}`, `equip {itemId, slot?}`, `unequip {slot}`, `use {itemId, targetPartId?, targetItemId?}` (бинт — на органическую часть тела; ремкомплект — на предмет или бионическую часть тела), `disassemble {itemId}`, `stairsDown` (на клетке портала — вход в портал), `stairsUp`, `rest` (отдых до восстановления или появления монстра — опционально).

`PlayerView` не раскрывает точные характеристики предметов неизученных типов: сервер сам формирует отображаемые значения (`??`, диапазоны) по статусу изученности.

Сервер валидирует каждую команду; некорректная команда возвращает `error` и не тратит ход.

## 8. Сессии и хранение

- Анонимная идентификация: при первом `hello` без токена сервер выдаёт случайный токен; клиент хранит его в `localStorage` и отправляет при подключении. Регистрации нет.
- На один токен — одна активная партия (и список завершённых для истории — опционально).
- Таблицы SQLite (примерно):
  - `players(token, created_at)`
  - `games(id, token, status: 'active'|'dead'|'won', created_at, updated_at, seed, snapshot_json, snapshot_turn)`
  - `commands(game_id, n, cmd_json)` — лог команд после последнего снапшота
- Сохранение: каждая принятая команда записывается в `commands`; каждые 50 команд и при отключении клиента — новый снапшот, лог до него очищается.
- Загрузка: снапшот + применение всех команд из лога через `applyCommand`. Тест должен проверять, что «снапшот + лог» даёт то же состояние, что и непрерывная игра.
- В памяти сервера держатся только партии подключённых игроков; через 5 минут после отключения партия выгружается.
- Если одна и та же сессия открыта в двух вкладках — новая вкладка вытесняет старую (старой отправить `error` и закрыть сокет).

## 9. Клиент и интерфейс

Раскладка экрана (десктоп, мобильная версия не нужна):
- Слева/по центру — карта на canvas, моноширинный шрифт, клетка ~ 12×20 px (подобрать). Цвета: стены серые, пол тёмно-серый, запомненные клетки затемнены, монстры — цветами по виду, игрок `@` белый, предметы — по типу (`)` оружие, `[` броня, `!` зелья, `?` бинты/ремкомплекты — или свои символы, записать в README).
- Справа — панель в стиле HUD киборга: имя, глубина, ход, общий HP (полоса), **диагностика тела** (список частей с пометкой материала — например `[Б]` для бионики, цветом стадии: зелёный / жёлтый / оранжевый / красный, и стадией текстом с учётом материала), экипировка с прочностью (`кинжал 34/40`, цвет по порогу эффективности; для неизученных типов — `~70%`).
- Системные сообщения ядра в логе визуально отличаются от повествовательных (цвет и/или префикс в квадратных скобках).
- Снизу — лог сообщений.
- Модальные окна (Vue): инвентарь, экипировка, навыки, выбор части тела для бинта, выбор предмета для ремкомплекта, создание персонажа, экран смерти.
- Осмотр монстра (`x` + выбор клетки или наведение мышью): название и видимое состояние его частей тела.

Управление:
- Движение: стрелки, numpad (1–9), vi-клавиши (`hjklyubn`). `.` или `5` — ждать.
- `g`/`,` подобрать, `i` инвентарь, `e` экипировка, `a` применить, `d` выбросить, `D` разобрать, `m` база знаний (навыки), `x` осмотр, `>` `<` лестницы и портал, `Esc` закрыть окно.
- Подсказка по клавишам — `?`.

Пока сервер не ответил на команду, клиент не отправляет следующую (простая блокировка ввода; предсказание хода в MVP не нужно).

## 10. Тесты и критерии приёмки

Тесты (Vitest), минимум:
- **Детерминизм:** одинаковый сид и одинаковая последовательность команд → идентичное итоговое состояние.
- **Снапшот + лог** = непрерывная игра.
- **Выбор части тела** распределён согласно весам (статистический тест с допуском).
- **Влияние ран по тегам:** искалеченная `grasp`-часть снижает точность; искалеченная `stance` снижает уклонение; одинаково для игрока и монстра; для `humanoid_fourarmed` потеря одной руки, не держащей оружие, не снижает точность.
- **Смерть** при обнулении `vital`-части и при обнулении общего HP.
- **Прочность:** износ брони только у предмета в слоте поражённой части; кривая эффективности по порогам; ремкомплект восстанавливает прочность.
- **Материалы тела:** бионика не регенерирует и не лечится бинтом/зельем; ремкомплект чинит бионику и не применяется к органике; органика регенерирует.
- **Изучение:** использование оружия продвигает и навык класса, и изученность типа; разборка даёт данные; `PlayerView` не содержит точных характеристик неизученных типов.
- **Победа:** вход в портал переводит партию в статус `won`, дальнейшие команды не принимаются.
- **Сообщения:** для всех монстров × всех частей тела × всех типов урона × всех исходов собирается текст без незаполненных плейсхолдеров; падеж и род правильные в нескольких контрольных примерах.
- **Сервер:** невалидная команда не меняет состояние и не тратит ход; клиент не получает невидимых монстров.

Критерии приёмки MVP (проверяются вручную):
1. `pnpm install && pnpm dev` поднимает игру, она открывается в браузере.
2. Можно создать персонажа с любой из двух формаций тела и любым стартовым оружием.
3. Можно пройти по 3 уровням, FOV и туман войны работают.
4. В бою сообщения указывают часть тела, оружие, исход; заметно, что раны меняют результаты боя (например, после того как волку искалечили лапу, он реже попадает и/или медленнее догоняет).
5. Снаряжение изнашивается, это видно в UI; ремкомплект чинит предметы и бионические части; бинт снимает стадию раны с органических частей.
6. Навыки растут от использования, это видно в базе знаний ядра; найденные предметы неизвестных типов показываются с `??` и постепенно изучаются; разборка работает.
6а. На 3-м уровне есть портал; вход в него завершает партию победой.
7. Закрыть вкладку посреди боя, открыть снова — партия продолжается в точности с того же состояния.
8. После смерти показывается экран итогов, старая партия больше не принимает команд, можно начать новую.
9. Все тесты проходят, `pnpm build` проходит без ошибок типов.

## 11. Вне рамок MVP (не делать)

- Боги, религия, алтари.
- Виртуальный терминал и улучшение бионических частей (заложена только модель данных `BionicUpgrades`, раздел 5.4). Валюта для улучшений тоже не нужна.
- Оружие и предметы из будущего (кроме ремкомплектов как части систем киборга).
- Магия, заклинания, свитки, кольца, амулеты.
- Дальний бой и метательное оружие.
- Голод/еда.
- Отрубание конечностей (тип заложить, механику не делать).
- Расы и статы (сила/ловкость/интеллект) помимо формации тела.
- Мультиплеер, регистрация, аккаунты, таблица рекордов.
- Мобильная вёрстка, тайловая графика, звук.
- Предсказание ходов на клиенте, дельта-обновления состояния.

## 12. Этапы работы

1. **Каркас:** монорепо, сборка, линт, тесты, пустые пакеты, `README.md`, `DECISIONS.md`. Сидированный ГПСЧ в `core`.
2. **Core: карта и движение:** генерация уровня, FOV, движение игрока, двери, лестницы, 3 уровня. Тесты детерминизма.
3. **Сервер и клиент (минимум):** WebSocket, токен, создание партии, отправка `PlayerView`, рендер карты на canvas, движение с клавиатуры. Хранение в SQLite, снапшоты и лог, переподключение.
4. **Тело и бой:** планы тел, монстры с ИИ, модуль формул (заглушка), модуль времени (заглушка), события боя, смерть. Панель частей тела в UI.
5. **Сообщения:** словоформы, шаблоны, рендер событий, лог в UI. Тесты сообщений.
6. **Предметы и прочность:** оружие, броня по слотам, износ, эффективность, расходники, ремонт, разборка, инвентарь и экипировка в UI, снаряжение монстров и выпадение.
7. **Ядро и тело киборга:** навыки, изучение типов предметов, база знаний в UI, материалы частей тела (органика/бионика), лечение и ремонт, создание персонажа, портал, экраны смерти и победы.
8. **Полировка:** осмотр монстров, подсказка по клавишам, проверка всех критериев приёмки из раздела 10, обновление README.
